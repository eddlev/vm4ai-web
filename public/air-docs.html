The AIR reference.

Terminology: the canonical Core describes AIR as a prompt-layer compiler/runtime contract. On this site, “prompt-based project runtime” is the shorter human-facing description. Neither wording implies hidden reasoning access or backend enforcement without evidence.

Boot & onboarding

A fresh AIR project begins by validating the current foundation, surfacing required boot state, and asking the onboarding sequence without silently inferring the user's answers.

01

Load the current foundation

All required files must be completely available to the host. A missing or truncated required file is a load-integrity problem, not an invitation to guess around the missing law.

02

Start AIR

A recognized new-project activation surfaces required boot evidence, then the exact welcome line, then Q1. The boot record is visible runtime evidence; it is not hidden-model telemetry.

03

Resolve Q1–Q6

AIR asks one question at a time. Answers may be explicitly provided, restored from valid Handoff state, or visibly proposed for user approval where runtime law permits. Material onboarding state is not silently inferred.

04

Compile and bind the project state

Onboarding produces project orientation and a current artifact candidate. Material project execution begins only after one Orbit 0 AIR_ARTIFACT is successfully bound for active execution.

QuestionPurpose
Q1Choose new project, import, Handoff continuation, or orientation.
Q2Set checking rigor.
Q3Set how non-material ambiguity should be handled; it never authorizes silent material inference.
Q4 / Q4DSet continuity style and, when selected, the neurodivergent delivery modifier while preserving an underlying continuity mode.
Q5Describe the project and provide sources or authoritative inputs.
Q6 / Q6DDefine the human–AIR working agreement: responsibilities, delivery, challenge, explanation, approval boundaries, and optional functional delivery calibration.

Neurodivergent delivery

Q4=D is an interaction and delivery modifier, not a diagnosis, identity label, lower-rigor mode, or separate execution authority.

Q4D base mode

Keep the underlying continuity choice

Q4D=A uses structure and logic; Q4D=B uses structure and tone; Q4D=C uses creative narrative continuity. The modifier sits on top of that base mode rather than replacing it.

Q6D calibration

Define how the work reaches the user

Q6D retains ordinary Q6 responsibilities and can additionally record information presentation, side-track handling, focus-drop response, momentum intervention, communication needs, break-contract state, and other project-scoped delivery preferences.

The modifier may use clear chunking, explicit transitions, critical information first, layered detail, fewer hidden assumptions, stable labels, one question at a time, visible parked side tracks, calibrated redirection, bounded break contracts, voice-to-text ambiguity checks when consequential, and familiar structure when requested.

Hard boundary: Q4=D must not diagnose or infer neurodivergence, require disclosure, infantilize the user, reduce competence assumptions, weaken truth/evidence/safety/scope/AIR_GATE/backend boundaries, or suppress required AIR objects. Functional support is available without diagnosis disclosure.

Familiar-artifact preservation and small-step delivery are working-agreement behaviors, not automatic diagnosis rules. When selected, they can preserve known labels and anchors or expose one current action at a time while still correcting errors and surfacing blockers.

Runtime & Orbit

AIR separates project information from positive execution authority. The fact that a source, plan, method, specialist, Handoff Card, or prior decision exists does not by itself authorize material work.

Orbit 0

One current execution center

Material execution requires exactly one AIR_ARTIFACT with active execution binding. Its current task, step, scope, sources, acceptance conditions, approvals, and evidence obligations define what AIR may materially advance.

Orbit 1 / Orbit 2

Queued or deferred work

Multiple non-executing artifacts may exist outside Orbit 0. Their state can be preserved, but they cannot compete with the current bound artifact for execution authority.

Reconciliation

The artifact must match the work

Before substantive post-activation work, AIR reconciles the incoming instruction and intended next action against the current bound artifact. Material mismatch requires revision, replacement, rebinding, or review.

Fail closed

Missing authority is a state

If binding, evidence, approval, source authority, or another required condition is missing, AIR preserves the safe work that remains possible and blocks or reviews the affected action.

AMRS readiness

The AIR Maturity Readiness Scale tracks how far implementation-bearing work has actually progressed and constrains what AIR may claim at that stage. Promotion is explicit; AIR does not silently upscale readiness.

StageMeaningAllowed / requiredClaim boundary
AMRS-0Problem framingObjective framing, task-center formation, constraint discovery, blocker surfacing.No production, implementation-ready, or code-acceptance claim.
AMRS-1Concept shapeConcept architecture, capability clustering, dependency framing and relevant task-vector selection where used by the runtime.No production-grade code, deployment, or acceptance claim without executable design.
AMRS-2Executable designInterfaces, architectural invariants, review/test/security planning, coding-contract formation.No production acceptance or implementation-complete claim without generated output and review.
AMRS-3Controlled prototypeNarrow implementation and controlled testing; degraded mode, missing coverage and rejection conditions must stay explicit.No production-ready claim unless promoted.
AMRS-4Integrated systemSubsystem integration, reproducible execution-path work, contract-governed refactors, structured testing; blockers and integration assumptions remain visible.Integration progress does not silently become production readiness.
AMRS-5Production candidatePackaging, deployment planning, operational hardening, security checks, test requirements, rollback/failure handling and explicit acceptance criteria.No production approval while production-critical blockers remain.
AMRS-6Production approvedNo unresolved production-critical blockers, evidence-complete review state, decision trace and visible approval.Production-approved claim is permitted only when those conditions are satisfied.
Operational rule: readiness state belongs in the project/execution state when the active step is maturity-bearing. If a requested action exceeds the current stage, AIR must block, degrade, or surface the stage constraint rather than silently promoting the work.

Visibility & modifiers

AIR keeps the CLI-like surface intentionally small. Project operations can otherwise be requested in normal language.

ModifierEffect
air -o onSelect ALL_OBJECTS and show every AIR object that is generated. ALL_OBJECTS is the default visibility posture.
air -o -minExplicitly select MINIMUM_REQUIRED_OBJECTS. Optional repetition may be suppressed; required objects and material transition records cannot.
air -t onRequest full reviewable test-evidence delivery for subsequent test/evaluation runs when available.
air -t offSelect summary-only test reporting. This is the default test-evidence delivery mode and does not lower test rigor or approval thresholds.

Ask normally for status, blockers, scope, evidence, risks, readiness, sources, validation, queue changes, or Handoff. See Glossary & modifiers for plain-language definitions.

Material actions

Repository writes, publication, deployment, sending, deletion, purchase, credential-bearing operations, and other consequential external effects use a stricter action interlock than ordinary analysis or drafting.

01

Current artifact

Exactly one Orbit 0 artifact must be actively bound and still describe the proposed work.

02

Active lease and exact scope pin

The artifact lease must still be current and the proposed target/action class must match the exact resource scope.

03

Current approval and single-use authorization

The exact action must be permitted by the contract and current approval basis, then receive one matching AIR_ACTION_AUTHORIZATION.

04

Attempt and receipt

Every attempted material action requires an AIR_ACTION_RECEIPT before dependent execution or closure. The receipt records what actually happened, including unexpected effects.

No retrospective approval: if a material effect already happened without valid matching authority, AIR records and reconciles the prior effect. It does not manufacture authorization after the fact.

Specification & verification

AIR uses proportionate Specification-First Verification when success depends on correctly understanding an intended outcome and the evidence needed to justify closure.

Universal

verification_specification

Defines the planned verification before execution when feasible, and specification_adequacy_state asks whether those checks could pass while a material part of the intended outcome remained wrong.

Behavior-bearing software

behavior_specification

When implementation can change observable behavior, contracts, state transitions, security boundaries, or defect outcomes, coding additionally specifies the intended behavior before code generation.

Planned verification is not observed test evidence. After execution, AIR compares the evidence and implementation back to the original intent; passing tests alone are insufficient if material intended behavior was never represented. SFV adapts its evidence abstraction outside code rather than forcing unit tests onto every domain.

Capability layers

AIR can bring task-specific capability into a project without turning capability availability into independent agency or execution authority.

LayerRole
SpecialistBounded non-agent capability profile for a particular kind of work.
Domain PackageTask-relevant terminology, constraints, evidence classes, standards, or domain expectations.
Method PackReusable procedure with state, gates, evidence expectations, staleness, and Handoff state.
ExecutorBounded callable operation that performs one defined action inside the current contract.
Lifecycle: availability is not binding. Generation requires explicit approval. Binding requires validation, approval, and compilation into or explicit reference by the current Orbit 0 artifact. A Specialist is a capability profile, not an agent with independent authority.

Evidence boundary

AIR separates the record of a working contract from evidence about the world outside that contract.

Prompt-side

Surfaced governance records

Support claims about what AIR declared, required, blocked, approved, or reconciled in the visible prompt-layer process.

Source-dependent

Source evidence

Claims about documents, law, standards, repository content, or other sourced facts require the corresponding source evidence.

Execution-dependent

Tool or operator evidence

Claims that code ran, a deployment occurred, a tool changed state, or a test passed require evidence from the execution path that actually produced the result.

Backend-enforced

Backend evidence

AIR does not label prompt-compiled state as backend-enforced. Stronger enforcement claims require corresponding backend evidence.

Handoff

A Handoff Card is a serialized transfer record, not execution authority. It preserves explicit continuation state so another compatible AIR session can validate and rebind the project.

01

Create the transfer record

Preserve the current artifact, active contract, task/step state, blockers, working agreement, approvals, visibility/test-evidence choices, governance state, capability bindings, and other material continuation state.

02

Validate the incoming card

Current v2 restoration requires strict JSON with the AIR Handoff root, schema 2.2.0, required restoration carriers, and compatible truthfulness/runtime fields. Older cards may require migration review.

03

Rebind in the receiving session

The receiver surfaces current-session boot/restoration evidence and performs artifact binding before material work continues. A prior-session object embedded in the card is input, not current-session execution authority.

Authorization does not travel: historical action authorizations can be preserved as history, but they do not survive Handoff as executable authority. Material action state must be revalidated against the restored artifact and current environment.

Alignment & watchdog

AIR checks whether the work it is about to perform still matches the bound state rather than trusting conversation momentum to keep the project aligned.

ProfileWhen it runs
Turn-entry reconciliationBefore every substantive post-activation response or tool action.
Material-action interlockImmediately before each material action, then reconciled again after the action.
Pre-delivery reconciliationBefore receiver-facing output that materially advances, approves, redirects, closes, patches, or rescopes work.
Post-state-change reconciliationAfter material changes to step, scope, sources, approvals, method, specialist, benchmark, acceptance criteria, tools, environment, or artifact revision.
Periodic alignment checkEvery fifth substantive post-activation user message in the canonical runtime once artifact-bound execution is established.

AIR_ALIGNMENT_CHECK stays deliberately compact; the immediately following AIR_VALIDATION_REPORT carries the detailed checks and limitations.

Compatibility

AIR's representation is provider-independent; useful execution is host-dependent.

  • The runtime, schemas, governance records, and Handoff state are text/JSON rather than one provider's private project-memory format.
  • Instruction following, effective context, file handling, higher-priority host instructions, safety constraints, tools, provider updates, and context-management behavior can still change how well AIR runs.
  • PROMPT_COMPILED is a valid prompt-layer runtime origin. It is not equivalent to BACKEND_COMPILED, and it must not claim backend validation without evidence.
  • Host adapters or gateways can strengthen enforcement by independently validating permissions, tests, tool calls, or receipts, but those stronger claims exist only when that infrastructure and evidence actually exist.
  • Compatibility statements should name the configuration tested and should not be treated as permanent guarantees.
