About AIR

The project should outlive the session.

AIR — AI Resource — grew from a practical problem: capable AI can help across many roles, but sustained project work still breaks down when scope drifts, state disappears into history, or a new session means starting the briefing again.

Origin

From filling capability gaps to carrying project state.

AIR began as an attempt to make a capable model useful as a cooperative resource across the kinds of skill gaps small teams repeatedly face. That raised harder questions than “can the model generate this?”: What is the current task? What is it allowed to do? What evidence supports the work? What remains unresolved? What happens when the session ends?

The framework evolved around those questions. AIR keeps one material task bound at a time, lets bounded Specialists, Domain packages, Method packs, and Executors add capability when needed, and serializes explicit project state into a Handoff Card when the container changes.

What transparency means here

Show the control state. Don’t pretend to show hidden reasoning.

AIR’s formal objects make declared task, contract, approval, evidence, validation, action, and continuation state inspectable.

Visible

Declared governance state

Objects can show what task is bound, what scope applies, which gate is open, what evidence is referenced, what approval exists, and what continuation state is being carried.

Not claimed

Private chain-of-thought or hidden telemetry

AIR does not claim access to hidden reasoning, neural activations, latent geometry, or backend enforcement merely because structured JSON appears in a response.

Continuity

The container can change. The work keeps its state.

The Handoff Card is the bridge: a strict-JSON transfer record containing explicit project state needed for another AIR session or platform to validate, restore, and rebind the work.

Fluid

Continue instead of reconstructing

The receiving runtime gets structured task, decision, constraint, blocker, evidence, approval, and next-step state rather than inferring the project from an entire transcript.

AIR

Not confined to one provider

The portable contract lives in AIR files and records rather than one vendor’s private project state. Host compatibility still has to be observed and validated; different models can produce different inference.

Principles

Honest by design.

The current framework is deliberately strict about the difference between useful structure and stronger guarantees it does not have.

Focused

One material task

Exactly one current Orbit 0 artifact supplies positive material execution authority. Queued and deferred work stays non-executing until explicitly promoted.

Evidence

Claims follow their support

Prompt records, source evidence, tool-observed evidence, and backend enforcement are different evidence classes and are reported as such.

Ambiguity

Don’t turn uncertainty into fact

Material user intent is clarified; externally verifiable uncertainty is evidenced or visibly review-gated.

Authority

Approval is scoped

Agreement with an idea does not silently authorize mutation, publication, deployment, binding, or another adjacent material action.

Continuity

State is explicit

Handoff carries declared project state forward and the receiving runtime revalidates/rebinds before execution.

Boundary

Prompt-based means prompt-based

AIR can materially structure model behavior without claiming deterministic enforcement or guaranteed correctness.

See the framework in the open.

AIR is Apache-2.0 at the framework-code layer. The current runtime contracts, packages, and release history are public.
