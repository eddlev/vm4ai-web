Reference

Glossary & modifiers.

The current AIR vocabulary in plain language. Status, blockers, evidence, readiness, validation, task switching, and Handoff can all be requested normally; only four system modifiers need command syntax.

Core idea

What AIR is and what its visible structure means.

AIR — AI Resource
A prompt-based framework for sustained AI project work. It compiles explicit task, evidence, approval, continuity, and review state into the host model's context before generation.
PROMPT_COMPILED
The default runtime origin for the public kit. AIR is being applied through the loaded prompt/runtime contract rather than independently enforced backend code. This is a claim boundary, not a simulated or inactive mode.
backend_validation_claimed: false
The default honesty boundary unless actual backend evidence establishes otherwise.
Fail closed
When a material requirement is unresolved—such as evidence, approval, source truth, binding, or authority—the affected action stops or enters review instead of being silently guessed through.
Blast radius
The adjacent systems, obligations, risks, or consequences a decision can affect. AIR uses blast-radius awareness to keep narrow task focus without becoming blind to nearby impact.

Foundation & boot

The files and checks that establish a current AIR session.

Five-file foundation
Core Runtime, Control Surface, Governance Supplement, Default Starter Profile, and Handoff Card Template. Current Core/Control/Starter are 2.4.3; current Handoff schema is 2.2.0.
Routine boot
The default ROUTINE_BOOT_MINIMUM_SUFFICIENT validation profile for a normal new/import project. It checks the smallest sufficient current foundation before onboarding instead of running a full release audit by default.
AIR load integrity
The requirement that the expected foundation identities, parsing/sentinels, schema compatibility, and required visible records are coherent enough for the current transition. Visible records are prompt-layer state evidence, not proof of hidden reasoning or backend execution.

Onboarding

The user-controlled project configuration before the first task is bound.

Q1
Entry path: new project, import an existing non-AIR project, continue from a Handoff Card, or explain AIR first.
Q2
Checking posture: light, balanced, or strict.
Q3
Preference for handling non-material ambiguity. It never authorizes AIR to invent material state.
Q4
Continuity mode: structure & logic, structure & tone, creative narrative continuity, or the neurodivergent delivery modifier.
Q4D
Conditional base continuity selection when Q4 chooses the neurodivergent delivery route.
Q5
Project intake: requested activity/deliverables, intended outcome when material, constraints, priorities, acceptance criteria already known, and initial sources. AIR does not demand a separate WHY when the intended outcome is already operationally sufficient.
Q6
Free-text AIR/user working agreement covering responsibility split, delivery form, challenge posture, explanation depth, approvals, assumptions to avoid, and related working preferences.
Q6D
Conditional functional calibration for neurodivergent delivery: information presentation, side tracks, focus, momentum, and communication needs. Diagnosis disclosure is optional.

Task state & binding

How AIR distinguishes the whole project from what is allowed to execute now.

Orbit 0
The sole current executing task/artifact. Positive material execution authority comes from exactly one current bound AIR_ARTIFACT.
Orbit 1
Queued or paused non-executing work with a return path or resume condition.
Orbit 2
Deferred non-executing work intentionally outside the current execution surface.
AIR_ARTIFACT
The canonical ACTIVE_EXECUTION_RECORD for the current material task. Other inputs affect execution only after being compiled into or explicitly referenced by it.
AIR_ACTIVE_CONTRACT
The explicit EXECUTION_CONTRACT: task center, scope in/out, allowed/prohibited actions, evidence, stop conditions, approval scope, sources, and binding state.
Active-state reconciliation
The 2.4.3 requirement to compare substantive incoming work and material delivery against the current Orbit 0 artifact before relying on or delivering it.

Capability

Bounded inputs that add expertise or procedure without becoming independent authorities.

Default Starter Profile
A conservative task-composite bootstrap/fallback capability profile. It can compile the first artifact candidate; it does not execute material work directly or govern in parallel with Core.
Specialist
A bounded capability profile for a class of work. Attachment or availability is not selection, approval, or binding.
Domain package
A domain overlay containing relevant terminology, constraints, standards, evidence expectations, or domain rules.
Method pack
A procedure with its own state and gates when applicable.
Executor
A bounded callable operation/capability. Executors are not agents and do not supply execution authority by themselves.

Governance, actions & evidence

The distinction between declared AIR control state and independent support for a claim.

AIR_GATE
A canonical DECISION_RECORD for a consequential transition or action. Gates can allow, review, reject, require evidence, or otherwise hold the affected path according to the governing contract.
AIR_ACTION_AUTHORIZATION
A single-use authorization record required before a material external action is attempted under the current action-governance law.
AIR_ACTION_RECEIPT
The observed-result record for an attempted authorized material action. Dependent execution or closure waits for the required receipt state.
AIR_PRIOR_EFFECT_RECORD
Recovery record for a material effect detected outside a valid current authorization path. Retrospective authorization is not allowed.
record_class
The exact canonical semantic identity of an AIR formal object. It is provider-invariant.
evidence_class
The support level behind a material claim: surfaced output, source-supported, tool-observed, or backend-enforced. It never replaces record_class.
SUMMARY_ONLY
Default test-evidence delivery mode. It reports scoped results and boundaries without pretending a full reproducibility package exists.
FULL_TEST_EVIDENCE
Opt-in evidence packaging for subsequent runs, enabled with air -t on, preserving available definitions, run identity, results, logs, fixtures, environment, and reproducibility classification.

Continuity

How explicit project state moves when the container changes.

Handoff Card
A strict-JSON TRANSFER_RECORD using current schema 2.2.0. It serializes explicit project/session continuation state for validation and rebinding in another AIR session or platform. It is not hidden model memory or execution authority.
AIR_ALIGNMENT_CHECK
The periodic anti-drift watchdog record. After artifact-bound execution begins, every fifth substantive user message triggers it together with an AIR_VALIDATION_REPORT.
Alignment recovery
The visible recovery surface used when established drift means affected governed work cannot safely continue against the current state.

Canonical modifiers

AIR keeps the command-like surface intentionally small.

air -o on
Explicitly select full object visibility. ALL_OBJECTS is already the default.
air -o -min
Select compact visibility. It may reduce optional repetition but cannot suppress required formal objects, transitions, gates, recovery, or periodic checks.
air -t on
Enable FULL_TEST_EVIDENCE for subsequent applicable runs.
air -t off
Use the default SUMMARY_ONLY test-evidence delivery mode.
Ask normally for everything else

Examples: “What is active now?”, “What is blocking this?”, “Show the evidence.”, “Is this ready?”, “Switch tasks.”, or “Make a handoff.”
