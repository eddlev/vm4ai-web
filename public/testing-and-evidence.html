How it works · Testing & evidence

Test the claim you actually want to make.

AIR uses different evidence paths for different questions. A behavioral model test, a deterministic release check, human QA and external verification can all be useful — but they do not prove the same thing.

Evidence map

Start with the thing you need to establish.

Choose the test for the claim — not the other way around.

What do you want to establish? → Use the matching test → record its evidence → make only the claim that evidence supports
Foundation / release integrity

Did the release package satisfy its defined checks?

Do this. Run the executable reproducibility harness.

Evidence. File identities, strict parsing, required values and markers, run records and matching decision fingerprints.

Supports. “The release passed the defined reproducibility checks under the recorded environment.”

Behavioral model operation

Does a live host model actually sustain AIR?

Do this. Run AIR in an isolated project/model test and exercise the relevant runtime behaviors.

Evidence. The observed session, AIR objects, failures, recoveries and test notes.

Supports. “AIR behaved as expected in this tested host/model configuration.”

Long-session stability

Does AIR hold its working contract over sustained use?

Do this. Run sustained project work and watch for state loss, runtime drift and recovery behavior.

Evidence. Session observations and the recorded points where AIR held, drifted, recovered or failed.

Supports. A bounded statement about stability in the configuration and test that actually ran.

Handoff continuity

Can recorded project state continue in a fresh session?

Do this. Create a Handoff Card, open a fresh compatible session, load the required runtime and card, validate, rebind and compare the restored state.

Evidence. The source state, Handoff record and receiving-session state after validation and rebinding.

Supports. “Recorded project state was restored in this test.” It does not prove hidden-state transfer or identical inference.

Host / model compatibility

Can this configuration run AIR usefully?

Do this. Test the complete foundation, sustained Orbit 0 work, required objects, approval/evidence boundaries, Handoff and visible drift recovery as relevant.

Evidence. A maintainer or field compatibility observation tied to a named host/model configuration.

Supports. “This tested configuration is compatible.” It does not certify every model or future version on that platform.

Real-world output correctness

Does the thing AIR helped produce actually work?

Do this. Use the external test appropriate to the output: unit or integration tests, source verification, security checks, deployment evidence, operator review, domain validation or another real-world check.

Evidence. Results from the external system, tool, source or reviewer.

Supports. Only the corresponding real-world claim. AIR’s prompt records are not a substitute for external proof.

Four evidence layers

Related, but deliberately separate.

No one layer is promoted into proof of another.

01 · Behavioral model testing

Test AIR inside a live model session.

This is the layer that asks whether a host model actually follows AIR’s runtime contract during real project work.

  • Use a dedicated project environment whose available memory/context is limited to that project.
  • Test prompts instruct the model not to use tools or access the web when the test requires that isolation.
  • Use one live test session for the run; delete it after the cycle to reduce contamination of the next run.
  • Maintainer QA is repeated across three separate project environments/cycles.

Boundary: repeated successful runs are evidence of observed stability. They do not make model inference deterministic and they are not an independent benchmark.

02 · Executable reproducibility

Test deterministic release properties separately.

The repository’s release-grade harness runs the same executable manifest three times in separate Docker containers with networking disabled, a read-only repository mount and recorded environment identity.

  • Checks include file hashes, strict JSON parsing, required strings and expected schema values.
  • Run records carry suite/input/source/environment identity and a decision fingerprint.
  • The comparator reports deterministic confirmation only when the required runs pass and their fingerprints agree.

Boundary: this proves the checks that ran against the recorded inputs and environment. It does not run or prove deterministic LLM inference.

03 · Human QA

Review the release as a product, not just a manifest.

Human QA covers questions executable checks cannot answer on their own: whether the documentation is coherent, the runtime behaves sensibly in use, a regression is acceptable, the website and repositories tell the same story, and a release is ready to ship.

Boundary: human review is legitimate evidence of review and acceptance. It is not independent empirical proof of claims the reviewer did not actually test.

04 · External verification

Prove claims about the world outside AIR.

If the claim is about repository state, code execution, deployment, a source, an operator action, a tool call, security, or another external condition, the evidence has to come from the corresponding external source or system.

Boundary: an AIR object can record the requirement or declared state. It cannot turn a prompt-side record into proof that the external event happened.

Behavioral QA

What the isolated project test is — and is not.

The model remains live on its host. The isolation is about the project environment and allowed context/tools, not about taking a cloud model offline.

Project isolation

Keep the test environment clean.

Each run is performed in a dedicated AIR project environment. The model is given the test material intended for that project rather than relying on unrelated project history or previous test sessions.

Tool / web boundary

Tell the model not to reach outside the test.

Where the behavioral test is intended to evaluate AIR from the supplied project material alone, the test prompt explicitly prohibits tools and web access. This is a prompt-level test condition, not Docker network isolation.

Fresh session discipline

Dispose of the run before the next cycle.

One session is used for a test run. When the cycle is complete, that session is deleted so the next project-folder run does not intentionally inherit the previous test conversation.

Three-cycle practice

Repeat observations; do not relabel inference.

Routine maintainer QA repeats the cycle across three isolated project environments. Agreement across those runs raises confidence in the observed behavior; it does not turn stochastic host-model inference into deterministic execution.

Portability and compatibility

The representation can travel. Execution still depends on the host.

AIR’s foundation, laws, schemas and Handoff state are text/JSON and are provider-independent at the architecture and representation layer. Useful execution is conditional on the host and model.

Portable by design

Nothing in the state format belongs to one model vendor.

AIR carries explicit project state and a prompt-side working contract rather than relying on a provider-specific hidden memory format. A Handoff can therefore be presented to another compatible system that can accept and interpret the required text and JSON.

Compatible in practice

The host still sets the ceiling.

Instruction-following capability, effective context and attachment limits, file handling, higher-priority host instructions, guardrails, tools, provider updates and context-management behavior can all affect whether AIR can run reliably.

Compatibility claim boundary

“Provider-independent architecture” is not the same claim as “works on every provider.” Compatibility observations should name the configuration that was actually tested.

Language discipline

Use the evidence word you earned.

Small wording differences carry different levels of certainty.

Observed

It happened in the stated test.

Use for a direct behavioral or operational observation tied to the configuration and conditions that produced it.

Repeated

It was observed across multiple runs.

Useful stability evidence, but not a synonym for deterministic inference.

Reproducible executable

The executable checks reproduced under recorded conditions.

Use for the release harness and other deterministic executable checks whose identities and outputs can be compared.

Maintainer-observed

First-party AIR development evidence.

Valid evidence when labelled honestly. It is not an independent benchmark, vendor certification or external endorsement.

Compatible

The tested configuration sustained the required AIR behavior.

State the host/model scope. Do not silently extend one successful configuration to an entire provider family.

Designed to

Architecture intent, not outcome proof.

Use for the behavior AIR is structured to encourage or require at the prompt layer when empirical or external proof is not being claimed.

Claim check

Read the result at the right level.

A passing test earns a bounded statement, not a larger story.

Supported

“AIR Kit v0.5.0’s release manifest produced matching decision fingerprints in three network-isolated Docker executions.”

Not supported by that test

“AIR has been proven deterministic.”

Supported

“Recorded Handoff state was restored after validation and rebinding in this tested session.”

Not supported by that test

“AIR transfers every hidden state and guarantees identical behavior on every model.”

The rule underneath all of this

AIR separates “the specification is intact,” “the host model followed the specification,” and “the resulting work is correct.” Those are different claims and they require different evidence.
