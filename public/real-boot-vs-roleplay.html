AIR load integrity

Updated August 2026 · VM4AI

AIR is prompt-based. That makes one question especially important: what can you actually verify when you load the framework into a host model?

The useful answer is narrower—and stronger—than “the JSON proves AIR is running.” A visible AIR boot can be checked for required prompt-layer structure, current file identity, schema coherence, and required formal records. Those checks improve confidence that the response is following the current AIR contract. They do not provide independent access to hidden reasoning or prove every runtime law was applied perfectly.

The failure mode

A capable model can recognize AIR terminology and produce prose that sounds structured without satisfying the current AIR surface. That is why the kit has explicit load-integrity, canonical-object, visibility, and fail-closed laws rather than relying on style or vocabulary.

The correct response to a suspicious boot is not to decide whether the model “really is AIR” by feel. Check the observable contract.

What a routine fresh boot checks

A normal new/import boot uses ROUTINE_BOOT_MINIMUM_SUFFICIENT. Before Q1, the current runtime checks the smallest sufficient foundation needed for a coherent start:

  • exactly one current authoritative file per foundation role;
  • expected canonical identities and current required versions;
  • Markdown sentinel presence / strict JSON parsing where applicable;
  • Handoff template schema consistency;
  • governance compatibility and active floor-invariant registry state;
  • normalized filename collision / duplicate-key state;
  • Default Starter compatibility with the active Core.

A normal boot does not need to run the full release-integrity audit merely to show Q1.

What you should see

When a normal new-project boot passes the required bootstrap checks, AIR surfaces the canonical boot-state records required by the current runtime, prints the exact welcome line, shows the fixed boot presentation mark, and asks Q1. Required formal objects must use their canonical object identities and required fields; they cannot be replaced by prose summaries or provider-native substitutes.

Observable evidence

A surfaced AIR_SESSION is a SESSION_STATE_RECORD. Its presence can support the claim that the required formal session record was rendered in that response. It does not, by itself, prove private chain-of-thought, neural state, backend enforcement, or an external action.

What visible objects do not prove

The current AIR floor is explicit:

  • surfaced AIR objects are governance records for the delivered output;
  • they do not claim hidden reasoning or chain-of-thought;
  • runtime_origin remains PROMPT_COMPILED unless actual backend evidence establishes otherwise;
  • backend_validation_claimed remains false without backend evidence;
  • source-dependent and execution-dependent claims require their corresponding evidence.

That means a model could still produce a structurally convincing formal object incorrectly. The object is inspectable declared state, not cryptographic attestation.

A practical check

  1. Use the current five-file foundation from the repository.
  2. Make sure the host receives the complete files rather than truncated excerpts.
  3. Start a new AIR project and verify the expected current boot sequence rather than accepting a prose-only imitation.
  4. Inspect formal objects for current identity/version/record-class and truthfulness fields.
  5. As the project proceeds, verify that material transitions actually produce the required gates, binding changes, alignment records, authorization/receipt records, or errors when those triggers occur.
  6. For claims about tools, repositories, deployments, tests, or external state, inspect the underlying source/tool/operator evidence rather than treating the AIR object itself as proof.

If a host cannot carry the contract

Some host/model combinations may refuse the files, truncate them, omit required surfaces, or otherwise fail the current contract. AIR treats compatibility as something to observe, not a permanent universal guarantee. If a host cannot satisfy the required foundation and formal surface, use another supported environment or report the behavior in GitHub Discussions.

The point

AIR’s assurance story is not “trust the JSON.” It is: make the control state visible, keep claims scoped to the evidence available, and fail closed when a material requirement cannot be established. That is a useful checkable boundary without pretending prompt-layer structure is backend attestation.
