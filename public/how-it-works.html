Operating model

How AIR works.

AIR is a prompt-based project runtime for governed, continuous AI work. It gives a compatible host model an explicit working contract before the work is generated: what is active, what is allowed, what evidence matters, what needs approval, and what state must survive the session.

Runtime position

AIR is part of the working context.

AIR is not a post-processing layer that waits for a raw answer and rewrites it afterwards. In prompt-compiled operation, the AIR foundation, project state, sources, conversation, tool results, and current request are all part of the context the host model interprets when it produces the next response or action proposal.

AIR's job

Govern the work.

Bind the active task, preserve scope and constraints, establish approval and evidence requirements, surface blockers, control delivery state, and keep continuation state explicit.

Host model's job

Perform the work.

Reason, draft, analyze, generate, call available tools, or execute through host capabilities inside the current AIR contract. Capability comes from the model and host; AIR structures how it is applied.

The short version

The model does the work. AIR governs the work.

Execution center

One material task is allowed to be current.

AIR keeps a single bound Orbit 0 artifact as the positive execution center. Other ideas, queued tasks, specialists, methods, and available tools do not acquire project authority merely because they exist.

Orbit 0

The work that may move.

The current artifact carries the task, scope, relevant sources, constraints, acceptance conditions, approval boundaries, and execution state for the material work in front of AIR.

Everything else

Available does not mean bound.

Queued work stays queued. Capability packages stay unbound until selected for task fit. A tool may be callable without being authorized for the current action. This separation prevents capability from quietly becoming authority.

Execution path

From request to reviewed result.

The exact ceremony scales with the stakes, but the ordering keeps high-consequence decisions ahead of execution.

01

Frame the project

Onboarding establishes the project, working agreement, rigor, ambiguity handling, continuity preferences, sources, and responsibility split. The detailed boot path lives on Get started.

02

Bind the active task

AIR narrows the next material unit of work into one current artifact so scope, authority, evidence requirements, and completion conditions have a single center.

03

Specify before consequential execution

Where the work changes behavior or carries material risk, AIR establishes what must be true and how that claim will be verified before treating implementation as ready to proceed.

04

Execute inside the contract

The host model performs the work with the sources, capabilities, methods, and tools that are relevant and permitted for the bound task. Missing authority, evidence, or required input blocks only the affected action.

05

Verify and review

AIR reconciles delivered work against the specification, evidence, acceptance criteria, and original intent. Tests and AIR records support only the claims their evidence actually establishes.

06

Continue or hand off

When the session ends or the work moves, a Handoff Card serializes the explicit continuation state. A receiving compatible AIR session validates and rebinds that state before material work resumes.

Assurance boundary

Governed does not mean magically guaranteed.

Prompt AIR can materially shape a capable host model's behavior, but the prompt layer is still interpreted by the host model. AIR therefore keeps its claims proportional to the evidence available.

What AIR can expose

A reviewable working contract.

Declared scope, task state, assumptions, gates, approvals, evidence posture, validation state, blockers, action records, and continuation state can be surfaced for inspection.

What AIR does not invent

Proof from a prompt record.

AIR does not claim hidden chain-of-thought access or deterministic backend enforcement in prompt-compiled mode. Claims about code execution, deployments, sources, security, tools, or other external events require corresponding external evidence.
