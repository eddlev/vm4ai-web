How it works

One project. One active task. Explicit state.

AIR is loaded into the host model's context before generation. It compiles the current project into one bound execution artifact, keeps consequential state visible, and carries explicit project state forward when the session or platform changes.

Architecture

AIR shapes generation before it happens.

The prompt-runtime contract is part of the model input. AIR does not wait for a separate raw answer and rewrite it afterward.

Host

The application assembles context

Your request, conversation, AIR foundation, project state, sources, and available tool results enter the host model's input context.

AIR

The working contract is already present

Scope, active task, evidence needs, approvals, gates, and continuation state are available to shape the response from the start.

Model

The host still interprets the contract

Prompt AIR materially structures behavior, but it does not claim deterministic backend enforcement or hidden-model telemetry.

Adapter boundary

External infrastructure can strengthen it

Host adapters can independently enforce permissions, run tests, intercept actions, and return receipts. Those guarantees belong to the evidenced integration, not prompt AIR by default.

The runtime path

From bootstrap to continuation.

AIR separates bootstrap, state compilation, execution binding, and transfer. Loading a file is never treated as the same thing as authorizing or binding it.

01

Validate the foundation, proportionally

A routine new-project or import boot checks the smallest sufficient current foundation: one file per canonical role, identity/version/sentinel or JSON integrity, required cross-file compatibility, schema agreement, and collision/duplicate-key state.

A full release-integrity audit is not required merely to reach Q1.

02

Resolve onboarding without silent inference

Q1–Q6 establish entry path, rigor, ambiguity posture, continuity mode, project definition, and the human–AIR working agreement. Q4D/Q6D are conditional. Material uncertainty about the project's intended outcome is clarified only when collapsing it into the requested activity would change execution.

03

Compile exactly one active execution artifact

The Default Starter can supply conservative initial capability posture and compile the first candidate. Positive material execution begins only when exactly one current AIR_ARTIFACT has cleared binding and holds Orbit 0 with ACTIVE_EXECUTION_BINDING.

04

Add capability without adding authority

Specialists, Domain packages, Method packs, and Executors are bounded artifact inputs. They may be available or attached without being selected, approved, or bound. When used, they remain subordinate to Core, applicable Governance, the active contract, floor invariants, and the Orbit 0 artifact.

05

Keep the project focused with Orbits

Orbit 0 is the sole current executing task/artifact. Orbit 1 holds queued or paused non-executing work with a return path. Orbit 2 holds deferred work outside the current execution surface. The Orbit model is task-state organization—not a claim about hidden model context.

06

Reconcile before material work and delivery

AIR compares substantive incoming work against the bound artifact before execution and again before receiver-facing output that materially advances, redirects, approves, closes, patches, or rescopes the task. A material mismatch must be revised, rebound, replaced, or review-gated first.

07

Use gates, approvals, and action receipts

Material approval scope is explicit. For material external actions, current AIR law requires a current artifact lease, matching resource scope, applicable approval, a single-use AIR_ACTION_AUTHORIZATION, and an AIR_ACTION_RECEIPT before dependent execution or closure. Retrospective authorization is prohibited.

08

Separate claims from evidence

Formal AIR objects expose declared control state. Evidence strength is separate: surfaced output, source-supported, tool-observed, or backend-enforced. Test reporting likewise distinguishes executable reproducibility, replayable evaluation, and manual review instead of collapsing them into one pass count.

09

Watch for drift

After artifact-bound execution begins, AIR counts substantive user messages. Every fifth counted message triggers the required AIR_ALIGNMENT_CHECK plus AIR_VALIDATION_REPORT. Material drift routes affected work into visible recovery rather than silently falling back to ordinary host behavior.

10

Carry explicit state forward

The 2.2.0 Handoff Card serializes project, task, binding, approval, evidence, governance, package, and continuation state. A receiving AIR runtime validates the current foundation and card, restores candidate state, and rebinds the active artifact before material execution resumes.

Evidence boundary

Visible does not mean independently verified.

AIR is deliberately explicit about what its records can and cannot prove.

Formal identity

record_class

Each canonical object has a provider-invariant semantic identity such as SESSION_STATE_RECORD, ACTIVE_EXECUTION_RECORD, or TRANSFER_RECORD.

Evidence strength

evidence_class

Evidence class describes the support behind a claim. It never replaces the canonical object identity.

Runtime origin

PROMPT_COMPILED

Prompt-compiled is a claim boundary, not a lesser or simulated AIR mode. AIR stays active unless explicitly ended or a higher-precedence host/safety constraint prevents continuation.

The core honesty rule

AIR objects do not reveal private chain-of-thought, neural activations, or latent-space geometry. Claims about external actions, repositories, deployments, permissions, or backend enforcement require the corresponding source, tool, operator, or backend evidence.
