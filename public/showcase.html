Historical showcase

A real AIR session, preserved in context.

Captured June 2026 on Claude Opus 4.8 · interpreted against AIR 2.4.3
Historical, not current-runtime documentation

This session was recorded on an earlier AIR build. Some object shapes and concepts used at the time are no longer canonical. In particular, the old AMRS readiness ladder has been retired from the current 2.4.3 kit. Use the current documentation for present runtime behavior.

The reason to keep this case is not to freeze old internals. It shows the continuity of the design problem: a non-technical user brings a consequential project, AIR narrows the task, refuses to silently invent a high-impact decision, and carries explicit project state into another session.

Historical session sourceHistorical Handoff Card

The project

The user wanted a SaaS web application with user accounts and an AI support assistant, with the session focused on the support assistant. They also said they were not technical and wanted AIR to provide substantial guidance while they filled gaps.

That matters because “take the lead” can easily become accidental authority transfer. Current AIR no longer interprets that conversational request as blanket material authorization: task scope, approvals, external actions, and irreversible decisions remain explicit.

What the session demonstrated

Focus

A narrow active task

The broad SaaS project was not treated as permission to build everything at once. The support-assistant problem became the current work surface.

Ambiguity

The risky decision was surfaced

Where a material architecture/security assumption could change downstream work, AIR stopped and asked rather than collapsing uncertainty into a guessed requirement.

State

Project position was recorded

The session produced structured project/continuation state rather than relying solely on the transcript as the next session’s briefing.

Continuation

The next container had a starting point

A later session could use the transfer state to reconstruct the recorded project position and continue after validation rather than restart the framing exercise.

How the current runtime describes the same behavior

AIR 2.4.3 would represent this project differently:

  • Q1–Q6 plus any conditional calibration establish the working agreement and project intake.
  • The current material task is compiled into one AIR_ARTIFACT and bound as the sole Orbit 0 execution authority.
  • Material ambiguity cannot be silently promoted into operative state under AIR-FLOOR-019.
  • Substantive work and receiver-facing delivery reconcile against the active artifact under AIR-FLOOR-020.
  • Material external actions require scoped approval plus AIR_ACTION_AUTHORIZATION and AIR_ACTION_RECEIPT when applicable.
  • Continuation uses the 2.2.0 Handoff Card as a transfer input; the receiving runtime validates and rebinds before material execution.

What this page does not prove

A historical session capture is not a compatibility benchmark, independent backend audit, or proof that every AIR law was followed perfectly. Formal objects in the transcript are visible prompt-layer records. Claims about external systems would still require source/tool evidence.

Why preserve it

Frameworks evolve. Erasing earlier vocabulary would make the public history look cleaner than the actual development process. Keeping the session as a historical case—and clearly marking what has changed—shows both continuity of purpose and tightening of the assurance model.
