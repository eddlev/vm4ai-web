Get started

Start AIR with five files.

No AIR account, agent platform, or installation is required. Load the current foundation into a capable AI interface, complete onboarding, and AIR compiles the first task into a bound project state.

The short path

Boot. Bind. Work. Continue.

The important boundary is simple: loading the files starts bootstrap. Material project execution begins only after AIR has a valid current artifact bound to Orbit 0.

01

Get the current foundation

Use exactly one current authoritative file for each foundation role: AIR_CORE_RUNTIME.md, AIR_CONTROL_SURFACE.md, AIR_GOV.md, AIR_DEFAULT_STARTER_PROFILE.json, and AIR_HANDOFF_CARD_TEMPLATE.json.

Open the current prompts directory →

02

Open a capable AI interface

Use a host that can receive the complete current foundation without truncation. Context limits, attachment behavior, and tokenization vary, so AIR does not publish a universal safe threshold or claim universal compatibility.

03

Start a new AIR project

Attach the five files and type Start a new AIR project. A routine new-project boot uses ROUTINE_BOOT_MINIMUM_SUFFICIENT: enough validation to establish a coherent foundation before Q1, not a full release audit.

On a valid normal boot, AIR surfaces the required boot state, prints Welcome to AIR., shows the fixed boot mark, then asks Q1. The activation wording never silently answers onboarding for you.

04

Complete deterministic onboarding

Q1 selects new project, import, Handoff continuation, or beginner orientation. Q2 sets review rigor; Q3 ambiguity posture; Q4 continuity mode; Q5 defines the project and sources; Q6 is the free-text working agreement. Q4D and Q6D appear only when the neurodivergent delivery route is selected.

When it materially changes execution, AIR distinguishes the activity or deliverable you requested from the outcome it is meant to achieve instead of inventing a purpose.

05

Bind the first active artifact

The Default Starter supplies a conservative initial/fallback capability posture and may compile the first AIR_ARTIFACT candidate. It is not a parallel execution authority. Material work begins only after exactly one valid artifact is bound to Orbit 0 with ACTIVE_EXECUTION_BINDING.

06

Work against current state

AIR reconciles substantive work against the bound Orbit 0 artifact, keeps material ambiguity unresolved until it is clarified or evidenced, and asks for the smallest exact missing input when something required is unavailable.

For material external actions, current AIR law also requires a matching authorization path and an observed receipt before dependent execution or closure.

07

Carry the project forward

A Handoff Card is a strict-JSON TRANSFER_RECORD using schema 2.2.0. It carries explicit project state into another AIR session or platform. The receiving runtime validates the card and current foundation, then rebinds execution state before material work continues.

The card is a transfer input, not execution authority, hidden model memory, or a guarantee of identical inference.

Is the boot valid?

Look for a coherent five-file load, matching current identities/schema, and the formal AIR records required by the current boot surface. A surfaced AIR_SESSION is a prompt-layer state record; its presence is useful evidence that the required surface was emitted, but it is not independent proof of hidden reasoning or backend enforcement.
